# Moteur de synchronisation (outbox + REST, Request bidirectionnel) — Design

## Intention

2e sous-projet de l'architecture distribuée (après la Fondation : Spring Modulith, `app.role`, `Syncable`/`syncId`, déjà livrée et approuvée). Construit le mécanisme réel de synchronisation entre un serveur client et un serveur partenaire/maître, validé sur la même tranche verticale que la Fondation : l'entité `Request`. Première validation sur 2 instances locales (ports différents) sur ce poste, avant tout déploiement NAS réel.

## Ce qui existe déjà (vérifié)

- `features/commun/` : `ServerRole`/`ServerRoleProperties` (`app.role`), `Syncable` (`syncId` UUID, généré à `@PrePersist`, `updatable=false`).
- `features/request/` : `Request extends Syncable`. `Comment` a déjà une distinction public/privé (`isPublic`) — mécanisme déjà en place, à réutiliser pour le filtrage de ce qui redescend vers le client.
- Spring Modulith en place (`ModularityTests` vérifie `commun`+`request`), avec un cycle transitif connu (`request → commun → customers → request`) — **non déclenché par ce sous-projet** (aucune nouvelle entité de ce sous-projet n'étend `Syncable`, voir Composants).
- Tailscale déjà actif sur le poste de dev (confirmé pendant le chantier Fondation), noms de machines résolubles par MagicDNS.

## Goals

- **Synchronisation bidirectionnelle de `Request`** entre un serveur en rôle `client` et un serveur en rôle `partner`/`master` :
  - **Client → Partenaire** : création/modification d'une `Request` côté client → mise en file d'attente locale (outbox) → envoi REST au partenaire dès que la connexion existe → ré-essai en cas d'échec.
  - **Partenaire → Client** : tout changement fait côté partenaire sur une `Request` (statut, assignation d'équipe/technicien, ajout d'un commentaire **public**) redescend vers le client pour un suivi en quasi temps réel — via **sondage périodique du client vers le partenaire** (le client appelle régulièrement le partenaire pour récupérer ses changements en attente), pas un vrai push serveur→serveur. Décision utilisateur : un sondage fréquent (quelques secondes) suffit pour cette 1ère version, et évite que le partenaire ait besoin d'initier un appel vers le client (voir authentification ci-dessous).
  - **Filtrage explicite** : les commentaires **privés** (`Comment.isPublic = false`) ne redescendent JAMAIS vers le client. Les assignations (équipe, technicien, statut) redescendent normalement — seul le contenu privé des commentaires est filtré, rien d'autre.
- **Détection de conflit** par version/horodatage : si un événement reçu porte une version de base qui ne correspond plus à l'état actuel (modifié des deux côtés pendant une coupure), ne pas appliquer automatiquement — créer une alerte pour le partenaire, qui tranche manuellement.
- **Gestionnaire de clés/licences centralisé côté maître, pas un secret figé en config** (décision utilisateur après relecture — un secret codé en dur dans un fichier de config ne serait pas gérable : pas de révocation, pas de rotation, pas de lien futur avec un abonnement) :
  - Le serveur maître/partenaire héberge un **registre central des clés** (`SecondaryServer` — voir Composants), qui génère, stocke et peut révoquer/faire tourner la clé de chaque serveur secondaire.
  - **Enrôlement initial (1er contact)** : l'admin génère, depuis l'interface du maître, un **code d'enrôlement à usage unique** pour le nouveau serveur secondaire. Ce code est saisi une seule fois dans la configuration du secondaire à son installation. Au premier démarrage, le secondaire appelle un endpoint d'enrôlement (`POST /api/sync/enroll`) avec ce code ; le maître lui délivre alors sa vraie clé API, que le secondaire conserve dans sa configuration locale (jamais exposée par une route applicative par la suite). Le code d'enrôlement est invalidé après ce premier usage.
  - **Sens des appels = toujours initiés par le secondaire** (décision utilisateur, résout aussi le problème d'authentification bidirectionnelle trouvé par la relecture) : c'est TOUJOURS le serveur secondaire qui appelle le maître/partenaire — jamais l'inverse. Le secondaire utilise sa clé pour (a) pousser son outbox (ses propres changements) et (b) interroger le maître pour récupérer les changements en attente le concernant (sondage périodique, voir Goals). Le maître n'a donc jamais besoin de "rappeler" un secondaire ni de présenter la moindre credential dans ce sens — seul le secondaire s'authentifie, toujours de la même façon.
  - La clé reste **révocable/rotable centralement** par le maître à tout moment (champ `statut` du registre, déjà prévu pour l'extension abonnement future) — contrairement à un secret de config statique, c'est le fondement technique qui permettra plus tard de couper l'accès d'un serveur dont l'abonnement s'est terminé.
- **Validation initiale sur 2 instances locales** (ports différents sur ce poste), avant tout déploiement réel sur NAS.

## Non-goals (pour ce sous-projet)

- **Aucune logique d'abonnement/facturation réelle.** L'utilisateur envisage, dans un 2e temps, de lier la validité d'une clé API au statut d'un abonnement (illimité, forfait, ou pourcentage des ventes — modèle encore à définir) : si l'abonnement se termine, le serveur secondaire doit s'arrêter de fonctionner. **Pas implémenté ici**, mais le registre des serveurs secondaires (voir Composants) prévoit un champ de statut explicite dès maintenant, pour ne pas fermer la porte à cette extension future.
- Pas de déploiement sur le vrai NAS dans ce sous-projet — validation locale uniquement.
- Pas de multi-tenance client (sous-projet séparé, à venir).
- Pas de login à froid hors ligne (sous-projet séparé, à venir).
- Ne retouche pas l'architecture Modulith (`commun`/`request`/`ticketing`) au-delà de l'ajout du nouveau module `sync` décrit ci-dessous — la dette connue (`request → commun → customers → request`) reste non traitée, elle n'est pas aggravée par ce sous-projet.

## Décisions prises par l'utilisateur

- Validation initiale = 2 instances locales, pas le NAS.
- Sync bidirectionnelle (pas seulement client→partenaire) : le client doit avoir un suivi en temps réel.
- Seuls les commentaires privés sont filtrés à la redescente — tout le reste (notamment les assignations) atteint le client normalement.
- Authentification = clé API par serveur secondaire, générée par le maître/partenaire à la configuration, saisie manuellement, jamais modifiable via l'application elle-même, empreinte seule stockée.
- Lien clé API ↔ abonnement : prévu pour plus tard, modèle de facturation encore à définir — ne pas implémenter, juste ne pas fermer la porte.

## Décisions laissées au porteur du plan (mon call, actées ici)

- **Nouveau module `features/sync`** pour tout le mécanisme (outbox, registre des serveurs secondaires, détection de conflit, alertes) — pas dans `commun` (déjà sujet à un cycle connu, pas besoin d'aggraver) ni dans `request`. `sync` dépend de `commun` (pour `Syncable`/`ServerRole`) et de `request` (pour lire/écrire `Request`/`Comment`) — dépendance à sens unique, `request` ne dépend PAS de `sync`.
- **Découplage `request` → `sync` par événements Spring** (pas une dépendance directe) : `request` publie un événement de domaine (ex. `RequestChangedEvent`) via `ApplicationEventPublisher` à chaque création/modification pertinente ; `sync` écoute cet événement et crée l'entrée outbox correspondante. Ce patron évite toute dépendance inverse `request → sync`, et s'appuie naturellement sur l'Event Publication Registry de Spring Modulith (déjà en place depuis la Fondation) pour la fiabilité de livraison (un événement publié mais non encore traité survit à un redémarrage).
- **Aucune nouvelle entité de ce sous-projet n'étend `Syncable`.** L'outbox, le registre des serveurs secondaires et les alertes de conflit sont des entités purement locales à chaque serveur, jamais elles-mêmes synchronisées — seule `Request` (déjà `Syncable` depuis la Fondation) traverse le réseau. La question en suspens de la revue finale de la Fondation (cycle `commun`↔`request` via `Syncable`) n'est donc pas aggravée ici, et reste à trancher avant qu'une AUTRE entité métier (pas une entité d'infrastructure de sync) n'étende `Syncable` à son tour.
- **Format de l'événement échangé** : JSON, enveloppe `{syncId, entityType: "Request", version, payload, originServerId}` — `payload` est une projection explicite (DTO), jamais l'entité JPA sérialisée brute, pour permettre le filtrage (commentaires privés exclus côté partenaire→client) et éviter de fuiter des champs internes.
- **Résolution des références croisées non-`Syncable`** (trouvé par la relecture — `Request` référence `Team`/`User` (assignation), `Customer`/`Contact`/`Site` (demandeur), aucun n'étend `Syncable` dans ce sous-projet) : le DTO de synchronisation **aplati ces références en champs d'affichage simples** (ex. `assignedTeamName`, `assignedToName` : texte, pas de FK) plutôt que de tenter de répliquer ces entités. Le serveur client n'a pas de ligne locale réelle pour l'équipe/le technicien du partenaire (ce sont des données internes au partenaire) — il affiche juste le nom reçu. Même logique dans l'autre sens si nécessaire plus tard.
- **Détection de conflit, côté PARTENAIRE UNIQUEMENT** (clarifié par la relecture — l'énoncé initial "alerte pour le partenaire" était ambigu sur QUI détecte) : chaque `Request` porte une version incrémentale (`@Version` JPA standard, optimistic locking) en plus de `syncId`. Le partenaire est la seule autorité de résolution : quand il reçoit un événement du client dont la version de base ne correspond plus à sa version actuelle (modifié par le partenaire pendant que le client était hors ligne), il NE L'APPLIQUE PAS automatiquement — il crée une alerte locale (le partenaire est toujours local à lui-même, pas de problème de routage). Le client, lui, ACCEPTE TOUJOURS la redescente du partenaire sans détection de conflit de son côté (le partenaire est l'autorité ; le client est un cache à jour, pas une 2e source de vérité) — ça évite le problème structurel (trouvé par la relecture) d'une alerte créée côté client qui ne pourrait jamais atteindre le partenaire censé la traiter.
- **Commentaires bidirectionnels** (trouvé par la relecture — le code existant permet déjà d'ajouter un commentaire des deux côtés, `RequestController` côté client/public ET `TicketController` côté partenaire) : un commentaire ajouté côté client remonte normalement vers le partenaire (jamais besoin de filtrage dans ce sens, un commentaire créé par le client est par nature visible du client) ; un commentaire ajouté côté partenaire ne redescend que s'il est public (`Comment.isPublic = true`), comme déjà décidé.
- **Déclenchement de l'événement de domaine SANS refactoriser les ~15 points d'écriture existants** (problème réel trouvé par la relecture : il n'existe aujourd'hui aucun point de passage unique pour les écritures sur `Request`/`Comment`, elles sont faites directement par 4 contrôleurs différents via `repository.save()`). **Solution : `Syncable` (donc `Request`) étend aussi `org.springframework.data.domain.AbstractAggregateRoot<Syncable>`** (patron Spring Data officiel, déjà conçu pour exactement ce cas : publier un événement de domaine de façon fiable à chaque `save()`, quel que soit l'appelant, sans toucher les points d'écriture). Chaque méthode mutante de `Request`/`Comment` appelle `registerEvent(new RequestChangedEvent(this))` ; Spring Data publie automatiquement les événements enregistrés au moment où N'IMPORTE LEQUEL des ~15 appels existants à `requestRepository.save(...)` s'exécute — zéro modification des contrôleurs existants. **Prévention de l'écho/boucle infinie** : l'événement applicatif d'un changement reçu PAR SYNCHRONISATION (pas par une action utilisateur locale) doit être marqué pour ne pas être re-publié vers son serveur d'origine — le listener qui applique un événement entrant écrit directement via le repository SANS passer par les méthodes mutantes qui appellent `registerEvent(...)` (ou vérifie `originServerId` avant de ré-émettre).
- **Registre des serveurs secondaires** (`SecondaryServer` : id, nom, rôle, URL Tailscale (informatif — jamais appelée par le maître, voir ci-dessus), empreinte de la clé API (le maître n'a besoin que de VÉRIFIER la clé présentée par le secondaire, donc une empreinte suffit ici — pas la même situation que l'ancien modèle bidirectionnel), **champ `statut` réservé pour l'extension abonnement future**, horodatages) — vit dans `features/sync`.
- **Transport, toujours initié par le secondaire** : côté maître/partenaire, 3 endpoints `@RestController` dans `features/sync` :
  - `POST /api/sync/enroll` (code d'enrôlement à usage unique → délivre la vraie clé API, invalide le code).
  - `POST /api/sync/events` (le secondaire pousse ses propres changements en attente, authentifié par sa clé API en en-tête `X-Sync-Api-Key`).
  - `GET /api/sync/events` (le secondaire récupère les changements du maître le concernant, authentifié pareil) — appelé en sondage périodique côté secondaire (`@Scheduled`, fréquence de l'ordre de quelques secondes).
  Côté secondaire : un job planifié (`@Scheduled` — le porteur du plan vérifie lui-même l'emplacement exact d'un patron `@Scheduled` existant dans ce dépôt avant de s'en inspirer, une référence antérieure à `QontoSyncScheduler` s'est révélée inexacte) qui pousse l'outbox local ET sonde le maître, avec backoff simple sur échec (pas de bibliothèque de retry externe pour cette 1ère version).

## Ce qui reste au porteur du plan

- Répartition précise en tâches (probable : 1. module `sync` + entités locales (outbox, registre, alertes) ; 2. événements de domaine côté `request` + écouteur côté `sync` qui alimente l'outbox ; 3. endpoint de réception REST + authentification par clé API ; 4. job de ré-essai + détection de conflit ; 5. validation bout-en-bout sur 2 instances locales).
- Détail exact du format JSON de l'événement et des DTOs de projection (`RequestSyncPayload` côté sortant partenaire→client, en excluant les commentaires privés).
- Écran admin (côté `/intra`) pour générer un code d'enrôlement et consulter/révoquer les serveurs secondaires enregistrés.
- Nom exact de la propriété de configuration où le secondaire conserve sa clé API reçue après enrôlement (ex. `app.sync.api-key`, dans un fichier non suivi par git, à l'image de `application-local.properties`), et de l'URL du maître à joindre (`app.sync.master-url`).
- Format exact du code d'enrôlement (ex. UUID court, durée de validité avant expiration si jamais utilisé).
- Tests de bout-en-bout sur 2 instances locales (2 profils Spring différents, 2 ports, 2 bases — ou 2 schémas dans la même base locale).
